# URL Shortener — DevOps Practical Assignment

Status: **Parts 1–3 complete and verified.** One known open item, not yet resolved: `kubectl
rollout undo` can desync `k8s/api-deployment.yaml` from the live cluster (see Part 2's Rollout and
rollback section for details).

## Components
- **API** — Python + FastAPI. Creates short URLs, redirects visitors to the original URL.
- **PostgreSQL** — stores URL mappings (source of truth).
- **Redis** — caches URL lookups (cache-aside pattern: check Redis first, fall back to Postgres
  on a miss, then write back to Redis).

## Endpoints

| Endpoint | Description |
|---|---|
| `POST /shorten` | Body: `{"url": "https://..."}` (max 2048 chars). Creates a short URL. Returns `{"short_code": "...", "short_url": "..."}`. |
| `GET /{short_code}` | Redirects (HTTP 302) to the original URL. Returns 404 if the code doesn't exist. |
| `GET /health` | Status, dependency reachability, version, uptime, and basic traffic counters — see below. Returns HTTP 503 (not 200) when a dependency is down. |
| `GET /live` | Bare liveness check — no dependency calls. Returns `{"status": "alive"}` if the process itself is responsive. |

**`GET /health` response shape:**
```json
{
  "status": "ok",
  "postgres": true,
  "redis": true,
  "version": "v2",
  "uptime_seconds": 12.0,
  "metrics": {
    "shorten_requests": 2,
    "redirects": 3,
    "cache_hits": 2,
    "cache_misses": 1,
    "not_found": 1
  }
}
```

Interactive docs (auto-generated by FastAPI) are available at `/docs` once the API is running.

**Design notes:**
- Short codes are base62-encoded Postgres row ids (not random strings) — deterministic, no
  collision handling needed, and no `short_code` column is stored (it's derived on every request).
- The API retries connecting to Postgres/Redis on startup (up to 30 attempts, 2s apart — widened
  from an initial 10 after a real cold-start crash on Kubernetes, see `documentation.md`) instead
  of assuming they're immediately ready.

## Part 1 — Run it with Docker Compose

**Requirements:** Docker with Compose (Docker Desktop, or Docker Engine + the Compose plugin).

```bash
# 1. Copy the example env file and adjust values if you want (defaults work as-is for local use)
cp .env.example .env

# 2. Build and start everything (API + Postgres + Redis)
docker compose up --build
```

This builds the API image, starts Postgres and Redis, waits for both to report healthy, then
starts the API. Once running:

```bash
# Health check
curl http://localhost:8000/health

# Create a short URL
curl -X POST http://localhost:8000/shorten \
  -H "Content-Type: application/json" \
  -d '{"url": "https://example.com/some/very/long/path"}'
# -> {"short_code":"1","short_url":"http://localhost:8000/1"}

# Use it (follow the redirect with -L, or drop -L to just see the 302 + Location header)
curl -L http://localhost:8000/1
```

Or just open `http://localhost:8000/1` (or whatever code you got back) in a browser — it redirects
directly.

**To stop:**

```bash
docker compose down          # stops and removes containers, keeps the Postgres data volume
docker compose down -v       # also wipes the Postgres data volume (full reset)
```

**Verifying Postgres data survives a restart:** create a short URL, then run
`docker compose down` (no `-v`) followed by `docker compose up -d` again — the same short code
will still resolve, because the data lives in a named Docker volume (`postgres_data`), independent
of the containers themselves.

## Part 2 — Kubernetes

**Requirements:** `kind` and `kubectl`. Everything runs on a local `kind` (Kubernetes-in-Docker)
cluster — no cloud account or managed database needed.

### 1. Create the cluster

```bash
kind create cluster --name url-short --config k8s/kind-cluster.yaml
```

The config maps host port `8000` to the node's port `30080` at cluster-creation time — this is
what lets the API be reached at `http://localhost:8000` later, the same address as Part 1.

### 2. Build and load the API image

`kind` runs its own container runtime, separate from your host's Docker — a locally built image
has to be explicitly loaded into the cluster (no registry needed for local dev):

```bash
docker build -t url-short-api:v1 ./api
kind load docker-image url-short-api:v1 --name url-short
```

### 3. Set up credentials

```bash
cp k8s/secret.example.yaml k8s/secret.yaml
# edit k8s/secret.yaml if you want a non-default password — "changeme" works for local use
```

`k8s/secret.yaml` is gitignored — same pattern as `.env`/`.env.example` in Part 1.

### 4. Apply everything

```bash
kubectl apply -f k8s/configmap.yaml -f k8s/secret.yaml \
  -f k8s/postgres-pvc.yaml -f k8s/postgres-deployment.yaml -f k8s/postgres-service.yaml \
  -f k8s/redis-deployment.yaml -f k8s/redis-service.yaml \
  -f k8s/api-deployment.yaml -f k8s/api-service.yaml

# watch everything come up
kubectl get pods -w
```

### 5. Use it — same as Part 1

```bash
curl http://localhost:8000/health
curl -X POST http://localhost:8000/shorten -H "Content-Type: application/json" \
  -d '{"url": "https://example.com/anything"}'
curl -L http://localhost:8000/1
```

### Design notes
- **Plain YAML manifests**, not Helm or Kustomize (all three are explicitly allowed) — no
  multi-environment variation exists in this assignment, so Helm's templating wasn't earning its
  complexity here. Tradeoff, acknowledged: plain YAML has no variables, so values like
  `POSTGRES_HOST`/`REDIS_HOST` in `k8s/configmap.yaml` have to be kept manually in sync with the
  actual Service names (`postgres`, `redis`) — mitigated by consistent naming discipline rather
  than tooling. Would reconsider Helm for a real multi-environment production deployment.
- **Postgres**: Deployment (not StatefulSet — single instance, no replication needed) with
  `strategy: Recreate` (required, not optional — the default `RollingUpdate` would hang trying to
  mount the `ReadWriteOnce` PVC from two pods at once), backed by a PVC using the cluster's default
  `StorageClass`. `subPath: pgdata` on the volume mount avoids a known Postgres-on-k8s issue with
  non-empty volume roots.
- **Redis**: plain Deployment, no PVC (cache — data loss on restart is correct behavior, not a
  gap), no auth configured (same simplification as Part 1, local-only scope).
- **API**: `readinessProbe` → `/health` (returns `503` when a dependency is down — verified this
  actually removes the pod from the Service's routing pool during a real simulated outage);
  `livenessProbe` → a separate `/live` endpoint with **no** dependency checks (a liveness probe
  tied to Postgres/Redis health would make Kubernetes repeatedly restart a perfectly healthy API
  pod during a database outage — restarting the API can't fix Postgres, so that would only add
  churn on top of an outage that readiness was already handling correctly).
- **Host access**: `NodePort` (not `kubectl port-forward`) — persistent cluster config, works
  regardless of any open terminal session; `port-forward` is better suited to ad-hoc debugging.
- **Resource requests/limits**: API and Postgres both `100m`/`500m` CPU, `128Mi`/`256Mi` memory;
  Redis lighter (`50m`/`200m` CPU, `64Mi`/`128Mi` memory) since it does less work per request.
  Reasonable starting points for a low-traffic local demo — not load-tested production sizing.

### Rollout and rollback

```bash
# roll out a new version: edit k8s/api-deployment.yaml's image tag, then
kubectl apply -f k8s/api-deployment.yaml
kubectl rollout status deployment/api

# roll back to the previous version
kubectl rollout undo deployment/api
kubectl rollout status deployment/api
```

**Known gap, not yet resolved:** `kubectl rollout undo` changes the live cluster but does **not**
update `k8s/api-deployment.yaml` — after a rollback, the file and the cluster can silently
disagree about which version is "supposed" to be running, until someone manually edits the file to
match (which is what was done here after testing rollback). This is a real risk (a later
`kubectl apply` of the stale file would silently undo the rollback). Not yet fixed with tooling —
options being weighed are a small script that rolls back and syncs the manifest atomically, or
GitOps (ArgoCD/Flux) for a real multi-environment setup, which is out of scope for this local
assignment.

### Verifying persistence and self-healing yourself

```bash
# create a short URL, note the code, then:
kubectl delete pod -l app=postgres    # kills it outright, not a graceful restart
kubectl get pods -l app=postgres -w   # watch the Deployment recreate it automatically
curl -L http://localhost:8000/<code>  # still resolves — data survived via the PVC
```

### Cleanup

```bash
kind delete cluster --name url-short
```

## Part 3 — Operate and troubleshoot

### Visibility

- **`GET /health`** is the primary signal — per-dependency status (`postgres`/`redis` booleans),
  overall `status`, the running `version`, process `uptime_seconds`, and basic in-memory traffic
  counters (`metrics`). Returns HTTP `503` (not `200`) when a dependency is down, so it works
  correctly as both a human-readable check and a Kubernetes probe target — not just a JSON body
  that happens to say "degraded" while still returning `200`.
- **`GET /live`** is a separate, dependency-free check used only for Kubernetes' liveness probe —
  see the Design notes above for why it's deliberately kept apart from `/health`.
- **Logs** — plain text (`kubectl logs -l app=api` / `docker compose logs api`), one line per
  create, cache hit, cache miss, and startup retry attempt, plus full tracebacks on unhandled
  errors.
- **Chose not to add**: a Prometheus `/metrics` endpoint or a Prometheus+Grafana stack. A raw
  metrics endpoint is only genuinely useful once something is scraping and storing it over time —
  which means running Prometheus, and likely Grafana on top, which is explicitly more than this
  assignment asks for ("does not need a full monitoring stack"). Folding a few counters into
  `/health` gives most of the practical value (current state + rough traffic shape) with zero new
  infrastructure.

### Runbook

Each entry below was tested against a real, deliberately-triggered failure, not written from
assumption — see `documentation.md` for exactly how each was reproduced.

#### 1. The API is running but requests fail

**What to check:**
1. `curl http://localhost:8000/health` (or the cluster/compose equivalent) first. If `postgres` or
   `redis` is `false`, this isn't an app bug — go to entry 2 below instead.
2. If `/health` says `"status": "ok"` but requests still fail, it's an app-level issue. Check the
   logs for a traceback.

**Commands:**
```bash
curl http://localhost:8000/health
kubectl logs -l app=api --tail=100          # Kubernetes
docker compose logs api --tail=100          # Docker Compose
```

**Real example (found and fixed during development):** a URL between 2049–2083 characters passed
Pydantic's own validation but exceeded the database column's 2048-char limit, causing a raw `500`
while `/health` stayed fully healthy the whole time. The log showed exactly why:
```
sqlalchemy.exc.DBAPIError: ... StringDataRightTruncationError: value too long for type character varying(2048)
```
Fixed by validating the length at the API boundary instead of letting bad input reach the
database. This is the pattern for this whole category of failure: `/health` isolates "is
everything downstream okay" from "is my own request malformed/triggering a code bug," and the
traceback in the logs tells you exactly which.

**Verify recovery:** retry the specific failing request and confirm success; confirm `/health`
stays `ok` throughout (proving it was never a dependency issue); if a code fix was needed, check
`/health`'s `version` field after redeploying to confirm the fix is actually live.

#### 2. The API cannot connect to PostgreSQL

**What to check:**
1. `/health` — `"postgres": false` confirms it's specifically Postgres (not Redis, not an app bug).
2. Is the Postgres pod/container actually up?
3. What do Postgres's own logs say?
4. Do the credentials in the Secret/ConfigMap actually match what Postgres was initialized with?
   **Known gotcha**: Postgres only applies `POSTGRES_USER`/`POSTGRES_PASSWORD` on the *first* init
   of an empty data directory — changing the Secret later without wiping the PVC leaves Postgres on
   the old credentials, and the API will fail to authenticate even though the Secret "looks right."
5. Does the Service actually have a live endpoint pointing at the pod?

**Commands:**
```bash
curl http://localhost:8000/health

# Kubernetes
kubectl get pods -l app=postgres
kubectl logs -l app=postgres --tail=50
kubectl get endpoints postgres
kubectl exec -it deploy/postgres -- pg_isready -U urlshortener -d urlshortener

# Docker Compose
docker compose ps postgres
docker compose logs postgres --tail=50
```

**Live-tested (Part 2):** scaling Postgres to 0 replicas reproduced this exactly — `/health`
flipped to `"status": "degraded", "postgres": false` within one health-check interval, and the API
pod's own readiness probe started failing (see entry 3).

**Verify recovery:** `/health` shows `postgres: true` again, then confirm with a real
create→resolve cycle (not just the flag) that it's actually functional, not just reachable.

#### 3. A Kubernetes pod is running but receives no traffic

**What to check:**
1. `kubectl get pods` — `READY: 0/1` (container `Running`, but not passing its readiness probe) is
   the signature of this exact scenario.
2. `kubectl describe pod <name>` — the Events section names the specific probe failure.
3. `kubectl get endpoints <service>` — confirms the pod's IP is genuinely missing from the
   Service's routing pool (this is Kubernetes correctly protecting traffic from a not-ready pod,
   not a bug in itself — the goal is finding *why* it's not ready).
4. Root-cause branches from there: a downstream dependency down (→ entry 2), the container
   crash-looping (`RESTARTS` climbing — check `kubectl logs --previous`), a misconfigured probe
   (wrong port/path), or `OOMKilled` from too-tight resource limits.

**Commands:**
```bash
kubectl get pods -l app=api
kubectl describe pod -l app=api
kubectl get endpoints api
kubectl logs -l app=api --previous     # only if RESTARTS > 0
```

**Live-tested (Part 2), real event captured:**
```
Warning  Unhealthy  kubelet  Readiness probe failed: HTTP probe failed with statuscode: 503
```
During that same test, `kubectl get endpoints api` returned no endpoints at all while the pod was
unready, and `RESTARTS` stayed at `0` throughout — confirming readiness (routing) and liveness
(pod lifecycle) reacted independently and correctly, as designed.

**Verify recovery:** pod back to `1/1 Ready`, `kubectl get endpoints` shows its IP again, and a
request through the Service actually succeeds end-to-end.

## Notes / assumptions / known limitations
- Short codes are sequential and therefore guessable — acceptable for this assignment's scope, not
  something to rely on for access control.
- No CI/CD pipeline — out of scope for the assignment's stated deliverables; would add a basic
  build+test GitHub Actions workflow as a stretch goal if time allows.
- No Prometheus/Grafana — deliberately chose in-`/health` counters instead; would stand up a real
  Prometheus+Grafana stack for genuine production monitoring (passive dashboards, alerting), which
  a point-in-time `curl` can't provide. See Part 3's Visibility section for the full reasoning.
- **Known incomplete item**: `kubectl rollout undo` can desync `k8s/api-deployment.yaml` from the
  live cluster (imperative command, doesn't touch the file) — happened once during testing, fixed
  manually that time. Not yet fixed with tooling; considered either a small script that rolls back
  and syncs the manifest atomically, or GitOps (ArgoCD/Flux) for a real multi-environment setup
  (the latter out of scope for this local assignment). See Part 2's Rollout and rollback section.
- Redis has no auth configured — acceptable for local-only scope, not something to carry into a
  shared environment as-is.
- Plain Kubernetes YAML manifests, not Helm — no multi-environment variation exists in this
  assignment to justify Helm's templating; would reconsider for a real production deployment across
  multiple environments. See Part 2's Design notes for the full tradeoff.
- See `documentation.md` for the full running decision log (why each choice was made, including
  every bug found and how) and `explanations.md` for concept write-ups (cache-aside, base62
  encoding, Docker/Compose/Kubernetes mechanics, etc.).
