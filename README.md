# URL Shortener — DevOps Practical Assignment

Status: **Part 1 (Docker Compose) and Part 2 (Kubernetes) complete and verified.** Part 3
(operations/runbook) not started yet.

## Components
- **API** — Python + FastAPI. Creates short URLs, redirects visitors to the original URL.
- **PostgreSQL** — stores URL mappings (source of truth).
- **Redis** — caches URL lookups (cache-aside pattern: check Redis first, fall back to Postgres
  on a miss, then write back to Redis).

## Endpoints

| Endpoint | Description |
|---|---|
| `POST /shorten` | Body: `{"url": "https://..."}`. Creates a short URL. Returns `{"short_code": "...", "short_url": "..."}`. |
| `GET /{short_code}` | Redirects (HTTP 302) to the original URL. Returns 404 if the code doesn't exist. |
| `GET /health` | Returns `{"status": "ok"|"degraded", "postgres": bool, "redis": bool}` — reports whether the API and each dependency are reachable. |

Interactive docs (auto-generated by FastAPI) are available at `/docs` once the API is running.

**Design notes:**
- Short codes are base62-encoded Postgres row ids (not random strings) — deterministic, no
  collision handling needed, and no `short_code` column is stored (it's derived on every request).
- The API retries connecting to Postgres/Redis on startup (up to 30 attempts, 2s apart — widened
  from an initial 10 after a real cold-start crash on Kubernetes, see `documentation.md`) instead
  of assuming they're immediately ready.

## Part 1 — Run it with Docker Compose

**Requirements:** Docker with Compose (Docker Desktop, or Docker Engine + the Compose plugin).

```bash
# 1. Copy the example env file and adjust values if you want (defaults work as-is for local use)
cp .env.example .env

# 2. Build and start everything (API + Postgres + Redis)
docker compose up --build
```

This builds the API image, starts Postgres and Redis, waits for both to report healthy, then
starts the API. Once running:

```bash
# Health check
curl http://localhost:8000/health

# Create a short URL
curl -X POST http://localhost:8000/shorten \
  -H "Content-Type: application/json" \
  -d '{"url": "https://example.com/some/very/long/path"}'
# -> {"short_code":"1","short_url":"http://localhost:8000/1"}

# Use it (follow the redirect with -L, or drop -L to just see the 302 + Location header)
curl -L http://localhost:8000/1
```

Or just open `http://localhost:8000/1` (or whatever code you got back) in a browser — it redirects
directly.

**To stop:**

```bash
docker compose down          # stops and removes containers, keeps the Postgres data volume
docker compose down -v       # also wipes the Postgres data volume (full reset)
```

**Verifying Postgres data survives a restart:** create a short URL, then run
`docker compose down` (no `-v`) followed by `docker compose up -d` again — the same short code
will still resolve, because the data lives in a named Docker volume (`postgres_data`), independent
of the containers themselves.

## Part 2 — Kubernetes

**Requirements:** `kind` and `kubectl`. Everything runs on a local `kind` (Kubernetes-in-Docker)
cluster — no cloud account or managed database needed.

### 1. Create the cluster

```bash
kind create cluster --name url-short --config k8s/kind-cluster.yaml
```

The config maps host port `8000` to the node's port `30080` at cluster-creation time — this is
what lets the API be reached at `http://localhost:8000` later, the same address as Part 1.

### 2. Build and load the API image

`kind` runs its own container runtime, separate from your host's Docker — a locally built image
has to be explicitly loaded into the cluster (no registry needed for local dev):

```bash
docker build -t url-short-api:v1 ./api
kind load docker-image url-short-api:v1 --name url-short
```

### 3. Set up credentials

```bash
cp k8s/secret.example.yaml k8s/secret.yaml
# edit k8s/secret.yaml if you want a non-default password — "changeme" works for local use
```

`k8s/secret.yaml` is gitignored — same pattern as `.env`/`.env.example` in Part 1.

### 4. Apply everything

```bash
kubectl apply -f k8s/configmap.yaml -f k8s/secret.yaml \
  -f k8s/postgres-pvc.yaml -f k8s/postgres-deployment.yaml -f k8s/postgres-service.yaml \
  -f k8s/redis-deployment.yaml -f k8s/redis-service.yaml \
  -f k8s/api-deployment.yaml -f k8s/api-service.yaml

# watch everything come up
kubectl get pods -w
```

### 5. Use it — same as Part 1

```bash
curl http://localhost:8000/health
curl -X POST http://localhost:8000/shorten -H "Content-Type: application/json" \
  -d '{"url": "https://example.com/anything"}'
curl -L http://localhost:8000/1
```

### Design notes
- **Plain YAML manifests**, not Helm or Kustomize (all three are explicitly allowed) — no
  multi-environment variation exists in this assignment, so Helm's templating wasn't earning its
  complexity here. Tradeoff, acknowledged: plain YAML has no variables, so values like
  `POSTGRES_HOST`/`REDIS_HOST` in `k8s/configmap.yaml` have to be kept manually in sync with the
  actual Service names (`postgres`, `redis`) — mitigated by consistent naming discipline rather
  than tooling. Would reconsider Helm for a real multi-environment production deployment.
- **Postgres**: Deployment (not StatefulSet — single instance, no replication needed) with
  `strategy: Recreate` (required, not optional — the default `RollingUpdate` would hang trying to
  mount the `ReadWriteOnce` PVC from two pods at once), backed by a PVC using the cluster's default
  `StorageClass`. `subPath: pgdata` on the volume mount avoids a known Postgres-on-k8s issue with
  non-empty volume roots.
- **Redis**: plain Deployment, no PVC (cache — data loss on restart is correct behavior, not a
  gap), no auth configured (same simplification as Part 1, local-only scope).
- **API**: `readinessProbe` → `/health` (returns `503` when a dependency is down — verified this
  actually removes the pod from the Service's routing pool during a real simulated outage);
  `livenessProbe` → a separate `/live` endpoint with **no** dependency checks (a liveness probe
  tied to Postgres/Redis health would make Kubernetes repeatedly restart a perfectly healthy API
  pod during a database outage — restarting the API can't fix Postgres, so that would only add
  churn on top of an outage that readiness was already handling correctly).
- **Host access**: `NodePort` (not `kubectl port-forward`) — persistent cluster config, works
  regardless of any open terminal session; `port-forward` is better suited to ad-hoc debugging.
- **Resource requests/limits**: API and Postgres both `100m`/`500m` CPU, `128Mi`/`256Mi` memory;
  Redis lighter (`50m`/`200m` CPU, `64Mi`/`128Mi` memory) since it does less work per request.
  Reasonable starting points for a low-traffic local demo — not load-tested production sizing.

### Rollout and rollback

```bash
# roll out a new version: edit k8s/api-deployment.yaml's image tag, then
kubectl apply -f k8s/api-deployment.yaml
kubectl rollout status deployment/api

# roll back to the previous version
kubectl rollout undo deployment/api
kubectl rollout status deployment/api
```

**Known gap, not yet resolved:** `kubectl rollout undo` changes the live cluster but does **not**
update `k8s/api-deployment.yaml` — after a rollback, the file and the cluster can silently
disagree about which version is "supposed" to be running, until someone manually edits the file to
match (which is what was done here after testing rollback). This is a real risk (a later
`kubectl apply` of the stale file would silently undo the rollback). Not yet fixed with tooling —
options being weighed are a small script that rolls back and syncs the manifest atomically, or
GitOps (ArgoCD/Flux) for a real multi-environment setup, which is out of scope for this local
assignment.

### Verifying persistence and self-healing yourself

```bash
# create a short URL, note the code, then:
kubectl delete pod -l app=postgres    # kills it outright, not a graceful restart
kubectl get pods -l app=postgres -w   # watch the Deployment recreate it automatically
curl -L http://localhost:8000/<code>  # still resolves — data survived via the PVC
```

### Cleanup

```bash
kind delete cluster --name url-short
```

## Notes / assumptions / known limitations
- Short codes are sequential and therefore guessable — acceptable for this assignment's scope, not
  something to rely on for access control.
- No CI/CD pipeline — out of scope for the assignment's stated deliverables; would add a basic
  build+test GitHub Actions workflow as a stretch goal if time allows.
