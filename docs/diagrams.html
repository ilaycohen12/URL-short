Cache-aside · base62 codes

How a request moves through the API, Redis and Postgres

Creating a link only touches Postgres. Opening one asks Redis first and falls back to Postgres on a miss, or when Redis is down. Postgres always has the answer; Redis only has copies.

Docker Compose · Kubernetes · networking

The same three parts, run two ways

Both setups serve the API on localhost:8000 and keep Postgres data outside the database process. Kubernetes adds two hops in front of the API, and the second one only forwards to pods that pass their readiness check.

Startup · readiness · liveness probes

How Kubernetes decides the API can take traffic

Three checks, three different consequences. Startup gives a slow start time to finish. Readiness removes the pod from traffic. Liveness restarts it. Only readiness looks at the database, so a Postgres outage pulls the pod out of service but never restarts it.

GitOps by hand · drift detection

Rolling back through git, and catching what went around it

Every change, a rollback included, starts in values.yaml; setup-k8s then makes the cluster match. Two commands can change the cluster without touching git. check-drift compares git against both places they write to.

Volumes · PVCs · stop vs reset

Where Postgres data lives, and which command deletes it

In both setups the data sits outside the Postgres process, so replacing the database container or pod is safe. What differs is how much a "stop" takes with it: in kind, the data is on the node container's own disk.

GitHub Actions

What runs on every push

A fast job checks the code first. Only if it passes do the slower jobs start a real Compose stack and two real Kubernetes clusters, using the same scripts a tester runs.
