## App

- **2026-09-23** — Decided on stack: **Python + FastAPI** for the API.
  - Why: built-in OpenAPI docs (covers the "document your endpoints" requirement), native async support (needed for non-blocking retries against Postgres/Redis on startup), small/readable codebase for the live demo/interview.
- **2026-09-23** — Endpoint design decided:
  - `POST /shorten` — body `{"url": "..."}`, inserts into Postgres, returns short code derived from the new row's id (base62-encoded), returns `{"short_code", "short_url"}`.
  - `GET /{short_code}` — checks Redis first (cache-aside), falls back to Postgres on miss, writes back to Redis, responds with HTTP 302 redirect to the original URL. 404 if not found anywhere.
  - `GET /health` — reports API status plus Postgres/Redis reachability. Used later for k8s probes and the Part 3 runbook.
  - Short code generation: base62-encode the Postgres auto-increment id, not random-string-with-collision-check — deterministic, no collision handling needed.
- **2026-09-24** — Documented the no-deduplication behaviour as a deliberate decision (README Part 1 Design notes + known limitations) after noticing the same URL gets a new short code on every `POST /shorten`. Cause is by design: each request is one `INSERT`, the code is the base62 of the new row id, there's no lookup by URL or unique constraint on `original_url`, and Redis only caches code → URL. Left as-is (matches per-user shortener semantics, the assignment only requires create + redirect) but wrote down the correct way to add it — hashed unique index, `INSERT ... ON CONFLICT` to avoid the check-then-insert race, and a URL-normalization decision — so it's a reasoned choice, not an unnoticed gap.
- **2026-09-24** — Reorganized README.md for a first-time reader: added a repo map and a Quick start (states up front that Compose and Kubernetes are independent alternatives that both bind `localhost:8000`, so only one runs at a time); merged the API usage into one "Using the API" section with bash/PowerShell examples side by side and a `/docs` walkthrough, replacing the curl examples duplicated in Parts 1 and 2; moved `/health`, `/dashboard`, a new per-counter metrics table and how to read them (`redirects = cache_hits + cache_misses`, client vs server errors, in-memory limits) into Part 3 → Visibility; merged all limitations into one list. Removed the "why no Prometheus/Grafana" explanation from the README at the user's request (the reasoning stays recorded in the 09-23 Part 3 entry above).
- **2026-09-24** — Added a keep-data stop option for Kubernetes, mirroring Compose's `down` vs `down -v`. Trigger: after `teardown-k8s` + `setup-k8s`, all short links were gone and ids restarted at 1 — correct for a teardown (it runs `kind delete cluster`, and the Postgres PVC lives on the kind node container's disk), but the README never said so, and there was no way to stop without losing data. New `scripts/stop-k8s.sh`/`.ps1` = `docker stop url-short-control-plane` (the whole kind cluster is that one container; its disk, including the PVC, is kept). `setup-k8s.sh` now detects a stopped cluster, `docker start`s it, waits for the node to be Ready, and ends with a `/health` retry loop (after a restart pods can briefly still show their pre-stop Ready status, so `kubectl wait` alone isn't proof). `teardown-k8s` unchanged in behaviour but now says explicitly it deletes all data. Rejected alternative: bind-mounting a host folder into kind for the Postgres data — survives even teardown, but Postgres on a Windows (NTFS) bind mount commonly fails with data-directory ownership/permission errors, and it's unusual for a throwaway local cluster. Also hardened the three `.ps1` wrappers: set `$ErrorActionPreference = 'Continue'` before calling Git Bash — with `Stop`, PowerShell 5.1 turns docker's normal stderr progress into a fatal `NativeCommandError` if the caller redirects `2>&1` (hit for real while testing); the exit code is what signals failure. Verified from PowerShell: created link `/4` → `stop-k8s.ps1` (node container `Running: false`, `kind get clusters` still lists it) → `setup-k8s.ps1` (took the "stopped - starting it" path, exit 0) → `/4` still 302s to its original URL, and the next new link was `/5` (sequence continued, not reset).

- **2026-09-23** (found during step 9 local sanity check) — Three real bugs caught before Part 1:
  1. `asyncpg==0.29.0` has no precompiled Windows wheel for Python 3.13 — pip tried to compile from C source and failed (missing MSVC Build Tools). Bumped to `asyncpg==0.30.0` (adds 3.13 wheels). Won't affect the Linux-based Docker image, but blocked local-outside-Docker testing.
  2. App startup looped forever with `greenlet` missing — SQLAlchemy's async engine needs `greenlet` internally, but plain `sqlalchemy==2.0.35` doesn't pull it in. Fixed by requiring the `[asyncio]` extra: `sqlalchemy[asyncio]==2.0.35`.
  3. **Real logic bug**: `GET /zzzzzz` (a validly-charactered but very large short code) returned `500` instead of `404`. `decode("zzzzzz")` = 32,590,299,105, which overflows Postgres's `INTEGER` column (max ~2.1B) — the DB rejected the query and the unhandled `DataError` surfaced as a 500. Fixed with an explicit bounds check (`0 < mapping_id <= 2_147_483_647`) in `main.py` before querying, so out-of-range codes get a clean 404 like any other not-found code.
- **2026-09-23** — Part 0 step 9 sanity check: ran the app locally (venv, not Docker) against throwaway `docker run` Postgres (port 5433) and Redis containers — not the eventual Compose stack, just enough to prove the app itself works end to end. Verified: `/health` (200, both deps true), full create→302-redirect flow, cache hit on second lookup, 404 on invalid/oversized codes, `/docs` loads. Throwaway containers removed afterward. Local `.env` (gitignored) left in place for future outside-Docker testing.
- **2026-09-24** — `bash scripts/setup-k8s.sh` failed from PowerShell with `kind: command not found`, even though the script had been verified on 09-23. Root cause: on this machine `bash` in PowerShell resolves to `C:\WINDOWS\system32\bash.exe` — **WSL's** bash, a separate Linux environment with its own PATH that can't see Windows-installed `kind`/`helm`/`kubectl`. The 09-23 verification had only ever run the script through Git Bash, so this path was never exercised — a testing gap, not a script bug. (First attempt, `bash .\scripts\setup-k8s.sh`, also failed separately: bash treats `\` as an escape character, so the path collapsed to `.scriptssetup-k8s.sh`.) Fix: added `scripts/setup-k8s.ps1` / `teardown-k8s.ps1` — thin wrappers that locate Git Bash via `git`'s install path and run the unchanged `.sh` scripts, so the setup logic stays in one place instead of being duplicated in PowerShell. Also added a preflight to `setup-k8s.sh`: checks `docker`/`kind`/`kubectl`/`helm` are on PATH and the Docker daemon is reachable, replacing kind's raw multi-KB `docker info` JSON dump with a one-line "start Docker Desktop" error (hit for real during this same verification). Verified from PowerShell itself, not Git Bash: `.\scripts\setup-k8s.ps1` → exit 0, all 3 pods ready, `/health` returned `version: v2` with Postgres and Redis true.
